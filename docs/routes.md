`page` starts at 1 and goes up to 1000; `limit` is 1–300 (default 100) and **exists only on the user lists**, which paginate over D1 — on every other route it is a 400 `UNSUPPORTED_PARAMETER`, because the response is a MAL page and slicing it would give a different result from what the same `limit` means in Jikan. Usernames accept only alphanumeric ASCII, `_` and `-`, up to 32 characters. Numeric IDs (anime/manga/character/producer/club) must be positive integers (400 otherwise). `:season` accepts `winter`/`spring`/`summer`/`fall`. Every response includes `meta`; errors include `error.code` and `requestId`.

**Query param validation (2026-07-30) — contract change.** Previously, a parameter a route did not implement was accepted and ignored: `?limit=5`, `?sfw`, `?sort=asc` and `?min_score=8` answered 200 with no effect at all, which is the kind of divergence a consumer has no way to detect. Now each route declares what it accepts in `src/http/query-contract.ts` and a middleware per route pattern refuses the rest, with two distinct codes: `UNKNOWN_PARAMETER` (a name that does not exist anywhere) and `UNSUPPORTED_PARAMETER` (exists in Jikan v4, not honored here — the message says why and points at the substitute). The distinction is the point: someone porting needs to know whether they got the name wrong or the feature does not exist.

**Fix of 2026-08-26 to that same promise of "pointing at the substitute":** the `sfw` message told you to use `"genres_exclude" or "rating"`, and `genres_exclude` is itself an entry in `UNSUPPORTED_PARAMS` — that is, the substitute on offer also answers 400, and following the advice cost a request to reach the same wall. It now points only at `rating`, with the caveat that it applies **only to anime search** (`manga.php` has no rating field; `buildTitleSearchParams` refuses `rating` outside anime). The test `never recommends a parameter that is itself refused` sweeps every message in the table and fails if any of them quotes a parameter the table itself refuses — the regression no longer depends on someone noticing.

`page` and `limit` stopped being silently corrected: `?page=0`, `?page=abc`, `?page=-5`, `?page=1.5` and `?page=1e9` become 400 `INVALID_PAGE` (the old `parseInt` read all of them as page 1, `1e9` included), and `?limit=99999` becomes a 400 instead of becoming 300. The 1000-page ceiling exists because each distinct number **fires a real request to MAL and writes a cache row** — measured at 1.5 s to 8.6 s for `?page=200`.

The table's coverage does not depend on discipline: `tests/routes/query-contract.test.ts` enumerates `app.routes` and fails if any GET route has no entry. A catch-all on `/v1/*` would not do — Hono composes middleware in registration order rather than letting the specific one override the generic, so the generic would reject `?q=` before the route that accepts it ran.

**`meta.pagination` on every paginated route (2026-07-30)**: `{ page, limit, count, total, hasNextPage }`. Before, only the user lists had it, and the other 17 returned a bare array — the consumer had to request the next page and see whether it came back empty. `total` is a number only on the user lists, which are counted in D1; elsewhere it is `null`, because the MAL page prints no total anywhere and deriving one from `lastVisiblePage × perPage` would be an invented number. `hasNextPage` comes from "the page came back at that family's native size" — cheap, and never costs the extra request that checking would.

**`genres/anime` and `genres/manga` started serving again on 2026-07-30, by changing the source.** The earlier block (500) was in the *sidebar* of the genre browse page (`/anime/genre/1/Action`), which MAL delivers truncated to ~12 items for requests coming from Cloudflare's network. The complete taxonomy is in the "Content Filter" block of the search page (`anime.php?cat=genre`), which does **not** suffer the reduction — verified by running the Worker on Cloudflare's real edge (`wrangler dev --remote`, config `jikan-edge-remote` in `.claude/launch.json`): 78 entries for anime and 79 for manga, `meta.stale: false`. The original symptom is still recorded in [docs/results/2026-07-26-genre-taxonomy-cloudflare-network-block.md](results/2026-07-26-genre-taxonomy-cloudflare-network-block.md).

The new source is richer than the old one, so the payload changed shape: each entry is now `{ malId, name, url, count, type }`, where `count` is the number of titles in that genre and `type` is MAL's category — `genres`, `explicit_genres`, `themes` or `demographics` (the same four as Jikan). `?filter=` accepts exactly those four values and filters the already-cached list (400 `INVALID_FILTER` for anything else). The order is the document's: category by category, alphabetical within each. The parser refuses the document if an entire category is missing or if fewer than 40 entries come back — the same "do not cache a partial taxonomy as complete" rule, now anchored on four signals instead of one.

**Content parity batch (2026-07-30) — contract changes.** A paired comparison against `api.jikan.moe/v4`: no route broken (all 98 answered 200), but the data came out impoverished or mislabeled. What changed:

- `genres`/`themes`/`demographics`/`studios`/`authors`/`producers`/`licensors` stopped being `string[]` and became `[{ malId, name, url }]`. The id was always in the href the parser took only the text from (`<a href="/anime/genre/1/Action">`). This closed a broken loop inside the API itself: `?genres=1` accepts an id, but no response returned one.
- `serialization` (string) became `serializations` (array) — a manga runs in more than one magazine.
- `aired`/`published` became `{ from, to, string }`, with a date only when the page gives day, month and year. Berserk is `"Aug 25, 1989 to ?"`, so `to` is `null` rather than invented. **Without** Jikan's `prop.from.{day,month,year}`, which is redundant with `from`.
- **`/v1/manga?q=` returns `volumes`, not `episodes`** — and this was not a dead field: the middle column of the manga results table is the **volume** count. Fullmetal Alchemist returned `episodes: 27`, and 27 is its volume count (chapters are 116). Right number, wrong label. `SearchEntry` became `AnimeSearchEntry`/`MangaSearchEntry` with their own cache versions.
- Added: `url` (canonical, with slug, via `og:url` — present on all seven detail pages; club and profile only have `og:url`, no `<link rel=canonical>`), `scoredBy`, `season`, `year`, `airing`/`publishing`, `broadcast`, `background`, `titleSynonyms` and `trailer`.
- `imageUrl` became the original on every route. 31 routes served the thumbnail MAL embeds in its own tables — 2,134 bytes where the same path has 56,653. The normalization lives in exactly one place (`imageFrom`, in `html.ts`); `pictures.parser.ts` stays out on purpose, because there `thumbnailUrl` is a field of its own.
- Added `images: { small, medium, large }` **only on the four details** for anime, manga, character and person. The CDN variants are **not uniform** — measured with two samples per type: anime and manga have `t` and `l`; a character has only `t` (the `l` is a 404); a person has only `l` (the `t` is a 404); a producer logo and a club image have none. Where none exists, the field is `null`, never a derived URL that breaks.
- Synopsis, `about` and `moreinfo` preserve paragraphs. `decodeHtml` replaced every tag with a space, so MAL's `<br>` became a space and the synopsis came out as a wall of text (Cowboy Bebop: 1,027 characters, zero breaks). Long fields moved to `richText`. In the same batch, the named-entity table gained what it lacked (`&mdash;` leaked raw in `/v1/anime/5114` and `/v1/manga/2`) and the **order** was fixed: tags are stripped **before** decoding, otherwise a user-written `&lt;b&gt;` became a real tag and got swallowed.
- New search filters: `sort=asc|desc`, `letter`, `min_score` (alias of `score`), `start_date`/`end_date` (`YYYY-MM-DD`) and `magazines` (manga only).

**`genres_exclude` was published and withdrawn on the same day — and the reason matters more than the filter.** The first probe compared only the **count**: `genre[]=12` returned 17 results and `genre[]=12&gx=1` returned 20, so I took it as confirmed that `gx` inverted the selection. Comparing the **ids**, 16 of the 18 results from `gx=1` are exactly the same entries as the list without inversion — MAL is ignoring the flag. Excluding a genre reliably would require filtering after the fetch, which would break the page size the route reports. It now answers 400 `UNSUPPORTED_PARAMETER` with that evidence in the message. The same investigation took down `producers`: the `p=` field exists on the page, but searching "gundam" with and without it returns the same set.

**Multiple `genres` is AND, not OR** — MAL's behavior, not our choice: for "love", genre 12 returns 16 results and 49 returns 3, but the two together return **zero**. An entry has to carry every id passed.

**`magazines` (manga only) uses `mid=` and accepts a single id**: "berserk" alone returns 50 results; with `mid=2` (Young Animal) it returns the 2 that actually run there.

**`order_by` went from 3 to 9 values**, each code checked against the result rather than against the legacy Jikan table: `start_date`, `score`, `episodes`/`volumes`, `end_date`, `type`, `members`, `rating`, `mal_id`. **`title` was left out on purpose** — code 0 returns the same order in both directions and it is not alphabetical, meaning MAL ignores it, and offering it would be a sort that does not sort.
- **`start_date`/`end_date` (2026-07-30, correcting a wrong verdict from the same day).** The first probe concluded "does not filter" and the parameter was even published as `UNSUPPORTED_PARAMETER`. **The probe was the thing that was wrong**: I ran it with an empty `q=`, which returns the default alphabetical dump, and I did not check the semantics of the result. Reading the search's real form, the fields exist and are six selects — `sm`/`sd`/`sy` and `em`/`ed`/`ey`, in **month, day, year** order. Redone with `q=naruto` and comparing id sets: `sy=2015&sm=1&sd=1` returns 50 results of which only 8 were in the unfiltered list, and the premiere dates check out in the detail (Aug/2015, Jul/2016, Apr/2017). `ey=2005&em=12&ed=31` returns only titles from 2003 to 2005. **One edge worth knowing**: an entry whose date MAL does not have (`Aired: Not available`) is **included** by either bound, not excluded — it was the only out-of-range result in both probes, and it is the source's behavior. **`genres_exclude` does not coexist with `genres`**: `gx=1` inverts the sense of every `genre[]` in the request rather than adding an exclusion — `genre[]=12` gives 17 results and `genre[]=12&gx=1` gives 20 disjoint ones — so passing both is a contradiction and is refused.

**`?filter=` on `top/anime` and `top/manga` (2026-07-30)**, mapped to MAL's `type=`. **The vocabulary differs between the two media, and this was measured, not deduced by symmetry**: anime accepts Jikan's four (`airing`, `upcoming`, `bypopularity`, `favorite`) and each one changes the top entry; manga accepts **only `bypopularity` and `favorite`** — comparing id sets, `publishing` and `upcoming` return exactly the same list as the unfiltered page (50 of 50 identical), because `topmanga.php` has no such tabs. Jikan lists all four for manga; two of them do nothing there. An invalid value is a 400 `INVALID_FILTER` with that medium's accepted list. **The validation is ours out of necessity**: MAL silently ignores an unknown `type=` and serves the unfiltered list with a 200, so passing the raw value through would turn `?filter=bogus` into a wrong list that looks right. The filter goes into the cache key.

**A deliberate divergence, not a gap**: `duration` keeps MAL's punctuation (`"24 min. per ep."`, against Jikan's `"24 min per ep"`) — it is what the page says, and this API reports the source rather than tidying it.

Known simplifications: `top/anime`, `top/manga`, `top/people`, `seasons/*` return lean fields (`AnimeListEntry`/`MangaListEntry`/`TopPersonEntry`), not the full detail — use `/v1/anime/:id`/`/v1/manga/:id`/`/v1/people/:id` for that. `character`/`producer`/`club` return basic metadata (name, image, favorites, etc.), without related lists of anime/manga/members/voice roles.

`GET /v1/top/people?page=` (implemented 2026-07-26) uses `people.php` without a query — the same URL whose search attempt (`?q=`) is already documented, but without `q=` it becomes the real "People" ranking by favorites (the same `ranking-list` class used by `top/anime`/`top/manga`), with native pagination via `limit=` (not `show=`, which is only used by the search). `GET /v1/top/characters?page=` (implemented 2026-07-26) follows the same pattern: `character.php` without `q=` is the real "Characters" ranking by favorites, with two extra columns (`animeography`/`mangaography`) listing the works the character appears in — each as `{malId, title}`, without image or role (that already exists in detail via `/v1/characters/:id/anime`). Native pagination via `limit=`, 50/page.

**`/v1/top/reviews` was not implemented — a deliberate decision, not a gap**: MAL has no mechanism whatsoever for ranking reviews by helpfulness/votes. `reviews.php` (used by `/v1/reviews/anime`/`/v1/reviews/manga`) has only one mode, ordered by publication date, with sentiment filters (Recommended/Mixed/Not Recommended) but no "sort by helpful" or equivalent — confirmed by inspecting the page's real filter form, which carries no alternative ordering parameter. Beyond that, the exposed date field (`class="update_at"`) has day granularity only (e.g. "Jul 26, 2026", repeated across several reviews from the same day), so it would not even be possible to reliably interleave the anime and manga feeds to simulate a unified route. Implementing `/v1/top/reviews` today would in practice be a redundant alias of `/v1/reviews/anime`/`/v1/reviews/manga` pretending to be a route with different semantics — the decision is not to do that until there is evidence of a real ranking mechanism.

`anime`/`manga` (search) accept `q` (1-64 characters) and, since 2026-07-27, **server-side filters verified one by one against MAL's real behavior**: `type` (anime: tv/ova/movie/special/ona/music; manga: manga/novel/lightnovel/oneshot/doujin/manhwa/manhua), `status` (airing|publishing/complete/upcoming), `rating` (anime only: g/pg/pg13/r17/r/rx), `score` (minimum, integer 1-10), `genres` (comma-separated ids, becomes a repeated `genre[]=`) and `order_by` (score/episodes|volumes/type — the column codes from the real sort links on the results table; always descending). Searching **by filters alone, without `q`, is valid** (e.g. `?genres=1&score=9`); `q` is only required when there is no filter at all (otherwise it would be a catalog dump). An invalid filter value → 400 `INVALID_FILTER` with the list of accepted values. `page` maps to MAL's native `show` parameter (`show = (page-1)*50`). **A note on MAL's behavior, not a bug**: for a text query with no real results, MAL does not return an empty list — it falls back to popular titles unrelated to the search. The parser faithfully reflects what MAL returns.

**Fix of 2026-08-27 — `?genres=` on its own returned an empty list, for anime and manga, for every id.** `/v1/anime?genres=1` answered 200 with `data: []` even though Action has 5012 titles by our own `/v1/genres/anime`. The cause is a redirect: when a single genre is the whole request, `anime.php?q=&genre[]=1` answers **301 → `/anime/genre/1/Action`**, the genre browse page, whose markup has none of the result rows the search parser looks for — and the parser returns `[]` instead of failing. **Only page 1 broke**: from page 2 on the URL carries `show=`, and any second parameter is enough to suppress the 301 (confirmed in production: `?genres=1` → 0 items, `?genres=1&page=2` → 50). The same holds for manga (`manga.php?q=&genre[]=1` → `/manga/genre/1/Action`).

Two things changed, because two were wrong. **The URL** now carries the `cat` field (`cat=anime`/`cat=manga`) — which is not a trick: it is an `<input type="hidden" name="cat">` from MAL's own search form that we were failing to send. Verified as neutral for the searches that already worked (same set and same order for `q=naruto`, `?type=tv`, `?score=8`, `?genre[]=1&o=3` and in the no-match query fallback; the ordering difference that showed up in one round reproduces between two identical calls *without* the field — it is MAL jitter). **The marker required on the fetch** was `filterByType`, which the genre page also contains — it has a type filter of its own — so the wrong page passed the guard. It is now the `<title>` (`Search Anime - MyAnimeList.net`/`Search Manga - MyAnimeList.net`), present even when the search legitimately found nothing, and absent from the genre page; a wrong page now gives a 502 `UPSTREAM_SUSPICIOUS` instead of a plausible wrong response. `ANIME_SEARCH_PARSER_VERSION`/`MANGA_SEARCH_PARSER_VERSION` went to `v2` — without the bump, the already-stored empty lists would keep being served until the TTL expired. Character and person search were **not** touched: their form also has `cat` (`character`/`person`), but they do not redirect, so sending it would be cache churn with no behavior change. Semantics checked, not just the status: all 50 items of `?genres=1` have Action in their detail, `?genres=10` returns Fantasy, and pages 1 and 2 are disjoint.

Pagination added 2026-07-27: `reviews/anime|manga?page=` (MAL's native `p=` parameter, 50/page) and `recommendations/anime|manga?page=` (native `show=` parameter, 100/page). `magazines?q=` filters locally over the already-cached full directory (the same pattern as `producers?q=`).

**Fix of 2026-07-30 to that prose**: the 50/page holds for the **global** list (`reviews.php`). The **per-title** reviews page (`/{type}/:id/x/reviews`) serves **20** — measured against `anime/1/x/reviews`, which carries 20 `review-element` blocks. **Fix of 2026-08-27 — `type` was `null` on every season entry.** The 891 entries of `seasons/now`, `seasons/upcoming` and `seasons/:year/:season`, plus the 130 of `schedules`, promised a field the parser filled with a literal `null` (`type: null` written in the code). The data was always on the page: each card carries its own medium in its class list, next to the `js-anime-type-all` they all have — `class="... js-seasonal-anime js-anime-type-all js-anime-type-5"`.

**The obvious anchor would be the wrong one.** The season page groups the cards under `<div class="anime-header">TV (New)</div>`, `ONA`, `Movie` and so on, and reading the header looks equivalent — but the `schedules` page reuses exactly the same cards under **weekday** headers, so there the header would say "Monday". The card's own class is the only source that works on both.

**The ids were resolved against three detail pages each, not deduced from the headers** — and that matters in two cases: `9` sits under a header that says "Special" but is `TV Special` in the detail, and `0` is MAL's own `Unknown` (61 of the 415 upcoming entries), not a parse failure. Map: `0` Unknown, `1` TV, `2` OVA, `3` Movie, `4` Special, `5` ONA, `9` TV Special. An id outside the table stays `null` rather than becoming an invented label. Checked live: 1,021 entries, zero `null`, and a sample of each type matches the `type` from the same anime's detail route. `SEASON_PARSER_VERSION` → `season-html-v2` and `SCHEDULE_PARSER_VERSION` → `schedule-html-v4`. New fixture `tests/fixtures/anime/season-now-real.html` with byte-for-byte real cards (including the `kids` and `r18` variants, which put extra classes before the type) under deliberately misleading headers — the old synthetic fixture has no `js-anime-type-all`, no header and none of those variants, so a parser reading the header would pass it.

**`/v1/anime/:id/streaming` can return empty in production even when the page has real data** — it is confirmed that the streaming-availability widget (JSON embedded in `data-raw`) is present on a direct fetch and absent on a fetch through Cloudflare's network for the same anime at the same moment. Not investigated in depth — low priority.

`characters`/`staff` come from the `/anime/:id/x/characters` page (or `/manga/:id/x/characters`) — **an important note**: that MAL route requires a non-empty slug segment in the URL (`/anime/{id}/{any-text}/characters`); omitting the slug returns a much smaller page without the characters/staff tables. Only the `id` matters for MAL's routing, so we use a fixed slug (`x`). `staff` is derived from the same characters page (no new fetch); manga has no `staff` (the equivalent is already covered by `authors` in the detail).

**Real bug fixed (2026-08-10): the Staff section was cut at a fixed 80 KB ceiling.** Confirmed live against One Piece (543 KB of staff, with no intermediate heading at all): the cut extracted 80 of the 542 real members — ~85% lost silently, with no error. The same class of error already fixed before in `backgroundSection`/`statisticsUrl` (a fixed byte window instead of cutting at the next real heading or at the end of the document). `CHARACTERS_STAFF_PARSER_VERSION` went from v2 to v3.

**`MAX_UPSTREAM_BYTES` rose from 2 to 5 MiB (2026-08-27) — the 2 MiB cut took down whole long-running series, with a 502.** Seven titles answered `502 UPSTREAM_SUSPICIOUS` on `/characters` **and** `/staff`, because both routes read the same page: One Piece (9.88 MB), Detective Conan (7.26), Naruto Shippuden (4.22), Pokémon (3.54), Bleach (3.04), Fairy Tail (2.54), Naruto (2.31). It was not a regression — neither row (`catalog:anime:21`/`:20`) had ever existed among the 106 `characters-staff` rows in D1, so there was never even a stale copy to serve. A side consequence: the 2026-08-10 staff fix above was validated against HTML downloaded **outside** the Worker, so in production it never actually ran on the very title that motivated it.

The cost of allowing those documents was **measured, not estimated**, with the real parsers over the real pages (8 documents, 0.87 to 9.88 MB): the parse is **linear at ~8.8 ms/MB** (no quadratic blowup in the regex passes) and the largest real page costs 85 ms and ~20 MB of heap — against ceilings of 30 s of CPU and 128 MB. The bottleneck is the **fetch**: 1.5 to 2.0 s for 2-3.5 MB, but 6.4 to 8.2 s for One Piece's 9.88 MB, against a `SOURCE_TIMEOUT_MS` of 8 s. Hence 5 MiB and no more: it covers five of the seven with wide timeout headroom, and leaves One Piece and Conan to a separate timeout change (which is a global knob, with a blast radius across every route — and `timeout` is still retried once in `mal-client.ts`, so an overrun costs ~16 s before the 504).

**Second stage (2026-08-27): a per-call fetch budget unblocks One Piece and Detective Conan.** The two that were left fit in neither 5 MiB nor 8 s. Rather than loosening the global limits for all 96 routes — where a runaway document would then go unnoticed everywhere — `MalClient.getHtml` accepts an optional third argument `{ timeoutMs, maxBytes }` and only the characters page fetch uses it (`CHARACTER_PAGE_BUDGET` in `src/source/fetch-policy.ts`: 20 s / 16 MiB). The global defaults stay at 8 s / 5 MiB.

The platform limits were **checked in Cloudflare's official documentation**, not assumed: an HTTP-triggered Worker **has no wall-clock ceiling** ("no hard limit on duration"), there is no per-subrequest time limit, and time spent waiting on `fetch` **does not count** as CPU time. So a long timeout costs no CPU and hits no duration limit. The only practical ceiling is the 30 s window the runtime gives in-flight requests when Cloudflare updates the runtime (a few times a week).

**That is why `timeout` stopped being retried when the budget is extended.** The retry exists for a transient blip on a short budget; on a generous budget that overran, repeating doubles an already long wait (20 s + 20 s = 40 s, past the 30 s window above) in exchange for a low chance of recovery. `upstream_error` still retries even on the extended budget — that one fails fast (connection refused/reset), so repeating is cheap. 16 MiB is deliberate headroom, not a snug fit around One Piece: the lesson of this whole investigation is that a tight ceiling turns normal source growth into a hard 502 on the day it is crossed.

The lock lease follows the budget (`refreshLeaseSecondsFor`, 50 s), for the same reason as `listRefreshLeaseSeconds`: a lease expiring mid-refresh lets a second request read the lock as abandoned and start a redundant 10 MB download in parallel.

**A method note, useful next time:** it was possible to time the real fetch from Cloudflare's edge without instrumenting anything, because the 502 already paid for the whole download. `mal-client.ts` reads `response.text()` **before** comparing the size, and MAL sends no `Content-Length` (a chunked response), so the cheap header check never fires and the 502's own latency was already the time to download the complete document. In other words: until now production was downloading One Piece's 10 MB on every request and throwing it away. Raising the ceiling adds no cost — it stops wasting what was already being paid for.

`GET /v1/users?q=&page=` was implemented 2026-07-26. **MAL behavior worth knowing**: a query that exactly matches a username makes MAL answer with a 303 redirect straight to the profile page (instead of the results list) — `MalClient` already follows redirects automatically, so the parser recognizes both possible shapes (a real list with the "User Search Results" marker, or a single profile page) and always returns a list, with 1 item in the exact-match case. **Club search is not viable through the public sources this project allows** — reconfirmed on 2026-07-26 with new evidence (the earlier attempt only had the "suspicious response" label, with no root cause). `GET /v1/producers/:id/full` (implemented 2026-07-26) fetches the same URL as `/v1/producers/:id`, but with a fuller parser that also extracts the description (`about`) and the external links (`external`) from the real page's "Available At" and "Resources" sections. `GET /v1/producers/:id/external` projects only the `external` field of `full` (no new fetch). **A real markup bug on MAL's side, not the parser's**: several hrefs in those sections carry a literal carriage return (`\r`) stuck before the attribute's closing quote (confirmed in the page's raw bytes, e.g. `href="http://pierrot.jp/\r"`); `z.string().url()` validates those URLs as valid anyway (JS's `URL` constructor discards those characters during internal normalization, but does not alter the original string), so without explicit handling the `\r` leaked into the response JSON. `GET /v1/characters?q=&page=` and `GET /v1/people?q=&page=` (implemented 2026-07-26) use `character.php`/`people.php`, confirmed as real server-side search (two real, distinct queries return completely different ID sets — unlike `clubs.php`). `GET /v1/characters/:id/anime`, `/manga` and `/voices` (implemented 2026-07-26) are derived from the same character detail URL (`character/:id`) — the three sections (Animeography, Mangaography, Voice Actors) already come together on the page, so a single fetch is reused for all three fields (the same pattern as anime's `characters`/`staff`). `GET /v1/people/:id/anime` (staff positions), `/manga` (credits as author) and `/voices` (voice roles) — implemented 2026-07-26, derived from the same person detail URL. `GET /v1/characters/:id/full` and `GET /v1/people/:id/full` (implemented 2026-07-26) close the characters and people groups. `GET /v1/anime/:id/reviews?page=` and `GET /v1/manga/:id/reviews?page=` (implemented 2026-07-26) use `/{type}/:id/x/reviews`, with native pagination via `p=`. **Different from the global `/v1/reviews/anime`/`/v1/reviews/manga` list**: the per-title page does not link back to the title itself on each review (it would make no sense, it is already implicit in the URL), so the payload has no `malId`/`title` — only the review's own data (user, avatar, date, tag, score, text). Trying to reuse the global list's parser unadjusted would make every review fail validation (empty title) and the whole route return empty — hence a dedicated parser (`title-reviews.parser.ts`) that reuses the same field extraction, just without the part that identifies the title.

`GET /v1/anime/:id/moreinfo` and `GET /v1/manga/:id/moreinfo` (implemented 2026-07-26) use `/{type}/:id/x/moreinfo` — free-form MAL curation notes (suggested watch order, trivia about prototypes/related works, expired licensing, etc.), extracted from `<h2 class="mb8">More Info</h2>` up to the start of the ads block. **Most titles do not have this section** (confirmed by testing several real IDs in production: Cowboy Bebop, Berserk and Trigun have content; Naruto and others return `null`) — the parser never throws on absence, it just returns `{ "text": null }`.

**`/v1/anime/:id/userupdates` and `/v1/manga/:id/userupdates` — implemented 2026-07-26, reversing the earlier exclusion with new evidence**: the original conclusion (correct) was that `/{type}/:id/{slug}/userupdates` does not exist as a MAL page of its own — any invalid sub-path falls back to the detail page. What the initial investigation had not noticed is that **the data itself is public on another page**: the recent member updates section lives on the same `/stats` page already used by `/statistics` (that is exactly where upstream Jikan extracts it from). The route now fetches the stats page (with its own cache key) and extracts the member rows. **A markup note**: the anime and manga variants of that page use different markup (anime: compact `class="ac"` cells; manga: multi-line `align="center"` cells with separate volume/chapter columns) — the parser anchors on the avatars (`image-member`) and tolerates both formats.

`GET /v1/users/:username/{full,about,friends,clubs,reviews,recommendations}` (implemented 2026-07-26) close the Users group. `about` and `full` are derived/combined from what already came from the profile page (no fetch beyond the components); `friends`/`clubs`/`reviews`/`recommendations` use the profile's real sub-pages. User reviews and recommendations reuse exactly the same parsers as the global lists (identical structure on MAL), with tolerance for an empty list — a user with no reviews is a valid `[]` result, not an error. **`/v1/users/:username/history` was not implemented — MAL's `/history/:username` page renders empty without login (confirmed in the project's original investigation); the equivalent data is already served by `/v1/users/:username/userupdates`, which comes from the profile's public "Last Updates" section.**

**`avatarUrl` and `about` were structurally always `null` (2026-08-27, found by the sweep of 124 calls).** Two independent defects on the same page, neither specific to any one user:

- **`avatarUrl` — a fixed prefix window, the fourth occurrence of that class in this repo.** The parser read `head = html.slice(0, 30_000)` and `class="user-image"` sits at around byte 30 thousand. That is: **which profile had an avatar was decided by a few dozen bytes of irrelevant markup above it** — measured on real profiles, Archaeon at 29,965 worked, AMayacrab at 30,047 did not, an 82-byte difference. The regex was always right; it just never saw the bytes. It now searches the whole document, which is safe because `class="user-image` appears **exactly once** on every profile checked.
- **`about` — a nonexistent anchor.** The search was `section(html, 'About Me', 12_000)`, and the literal string `About Me` **does not exist anywhere** on a MAL profile. The field could only be `null`, for every user — `/v1/users/:username/about` was a route incapable of returning anything else. The real container is `<div class="user-profile-about ...">` → `<div class="word-break">`, and it **disappears** when the user has written nothing (confirmed: of the five real profiles measured, the three with an About had exactly one container, the two without had none) — which is why absence genuinely means `null`, not a search that missed.

The content is read by **`<div>` depth** (`divContent` in `html.ts`, a new shared helper), not up to the first `</div>`: an About frequently opens with a nested div (a centered image is the common case), and stopping at the inner closing tag returned the wrapper's markup with no text at all. `PARSER_VERSION` went from `user-html-v4` to `v5` — required, because every profile cached under v4 stores `null` in both fields.

**Why the suite did not catch it**: `tests/fixtures/users/profile-valid.html` is 6,565 bytes — the whole fixture fits inside the 30 KB window, with `user-image` at byte 162, so the avatar passed the test and failed in production; and it contains neither `About Me` nor `word-break`, so the About path was never exercised. Exactly the "a synthetic fixture hides a missing field" risk already recorded in `CLAUDE.md`. Added `tests/fixtures/users/profile-real.html`, a byte-for-byte capture of a real profile (94 KB, avatar at byte 30,040, About with a nested div) — without it the fix would have no test capable of failing.

**Profile parsing fix (2026-07-27, reported by a real consumer during a port)**: the user statistics parser captured the **bar chart's pixel widths** (`width: 221.9px`) instead of the real counters — the numbers looked plausible because the chart is proportional, but they were wrong (e.g. completed 221 when the real value was 233). On top of that, `episodesWatched`/`chaptersRead`/`volumesRead` always came back `null` because the page's real labels are `Episodes`/`Chapters`/`Volumes` in separate spans, not `Episodes Watched:`/`Chapters Read:`. Fixed by anchoring the counters on `>Label</a>` and the totals on `>Label</span><span>`; the old synthetic fixture was replaced with markup copied from the real page. In the same batch: favorites and userupdates started emitting `malId` (camelCase, like the rest of the API — it used to leak `mal_id`), anime/manga favorites gained `startYear` (from `<span class="users">TV&middot;1998</span>`), `PARSER_VERSION` rose to `user-html-v2`, and `withCache` now treats a `parser_version` mismatch as a non-fresh cache (the version used to be written but never compared, so wrong data survived until the TTL).

**Missing statistics fields (2026-07-30, the same class as the bug above)**: `daysWatched`/`rewatched` (anime) and `daysRead`/`reread` (manga) were never emitted, so consumers expecting parity with Jikan got `null`/absent and fell back. It was not a source limitation: all four values are in the same profile HTML we already fetch (the fixture `tests/fixtures/users/profile-valid.html`, copied from the real page, already contained `Days: 12.5`, `Rewatched 1`, `Days: 3.1`, `Reread 0`) — the 2026-07-27 sweep simply did not cover them. `Rewatched`/`Reread` use the existing `dataValue` helper unchanged; `Days` needed a third regex format because it is **the only stat whose value sits outside a span** (`<span class="fn-grey2 fw-n">Days: </span>12.5`), different from both `>Label</span><span>value</span>` and `Mean Score:` (which wraps the value in `<span class="score-label">`). It is a fractional value, so the pattern accepts `.`. `PARSER_VERSION` rose to `user-html-v3` to invalidate already-cached profiles — `/v1/users/:username/statistics` reads the `user_statistics` row in D1 written by the profile refresh, so without the bump the old data (missing the fields) would survive until the 6 h TTL. No migration: the statistics are JSON in `anime_json`/`manga_json`. A side note: `site/index.html` already advertised `daysWatched` in the route grid example — now the example matches the real response.

**Leakage between the anime and manga blocks (2026-07-30, third round on the same bug)**: the two earlier fixes got the regexes right but kept `section(html, 'Anime Stats', 8_000)` — a fixed 8 KB window. On the real page `Manga Stats` sits ~2 KB from `Anime Stats`, that is **inside** the window, so the anime block could see the manga numbers. As long as every line exists the regex finds the anime match first and the result comes out right — but MAL only has to rename or omit a line for the manga value to be served as if it were the anime's, with no error at all. Reproduced in a test: removing the `Completed` line from the anime block, the old parser returned `4` (the manga's `completed`) instead of `0`. Fixed with `statsSection`, which cuts the anime block at the `Manga Stats` heading, and `statsList`, which restricts each lookup to the `<ul>` the line belongs to (`stats-status` for the status counters, `stats-data` for the totals) — this also closes a second path: generic labels like `Completed` and `Episodes` no longer reach the `Last Anime Updates` feed, which sits in the same section and repeats the same words. `PARSER_VERSION` did **not** rise (still `user-html-v3`): for well-formed pages no emitted value changes, so a bump would only cost a mass refetch. In the same batch, `withCache` gained test coverage (`tests/services/cacheable.test.ts`) — `parser_version` invalidation was in production with no test at all.

**User lists: the modern layout and silent truncation (2026-07-30)** — discovered by a sweep of every route in production, not by a report. `GET /v1/users/:username/animelist` and `/mangalist` returned **502 `UPSTREAM_SUSPICIOUS`** (`List snapshot rejected: empty_list_without_explicit_empty_marker`) for every user with the modern list layout — which is the user's own choice in MAL's settings, so there was nothing wrong with the page. The parser recognized only `class="animetitle"`, markup exclusive to the **classic** layout; in the modern one MAL delivers the entries as JSON inside the `data-items` attribute. The completeness guard was right all along: matching zero items, it refused to store an empty list as complete. Correlation measured on real users: modern → 502 (Xinil, Karinyia, jet2r0cks), classic → 200 (Zel, AMayacrab).

While investigating, a **second bug turned up, worse for being silent**: without a query param the modern layout's page carries only **one** entry (the rest would come from `load.json`, an internal endpoint barred by the source policy), and the classic one carries *fewer rows than the profile declares* — AMayacrab served **273 of 360**. The public URL `?status=7` (the "All" tab) fixes both cases: the modern layout starts rendering blocks of 300 entries in `data-items`, and the classic one returns all 360. Pagination via `&offset=` in blocks of 300 happens **only in the modern layout**; the classic one ignores the offset and returns everything in a single document, so the loop stops on the first page. A ceiling of 10 pages per refresh — that is the limit of one user's list, not a sweep of MAL.

Fields the classic layout never carried now come populated when the source is the modern layout: `status` (vocabulary `watching`/`reading`, `completed`, `on hold`, `dropped`, `plan to watch`/`plan to read`), `total`, `startedAt`, `finishedAt` and `updatedAt`. **A deliberate asymmetry**: in the classic layout those fields stay `null`, because the page does not expose them the same way — we prefer an honest `null` to an invented value. *(`total` left that list on 2026-07-30 — the classic page **does** have the number, in the same progress cell; see the progress-cell note below.)* Zero is MAL's "undefined" for score, episodes and chapters, so it becomes `null` and not `0` (One Piece has `anime_num_episodes: 0` because it is still airing). The dates come as `MM-DD-YY` without a century and are converted with a pivot on the current year (`10` → 2010, `98` → 1998). `LIST_PARSER_VERSION` (`user-list-html-v2`) is separate from the profile's `PARSER_VERSION`, so a list fix invalidates only the cached lists instead of dragging the whole profile and statistics along. Validated against the complete real pages, not just the fixture: 300+99 = **399** unique entries for Xinil and **360** for AMayacrab — exactly the `totalEntries` that `/statistics` reports for each.

**A numeric title arrives as a JSON number (2026-07-30)** — discovered only after the modern layout was deployed, with Karinyia still at 502 (`invalid_list_item`). MAL does **not add quotes** when a title looks like a number, so `86` (the anime *86 Eighty-Six*), `1` and `663114` arrive as numbers, not strings. Reading only strings emptied the title, and an empty title fails the entry's schema — since one invalid item rejects the whole page, **a single anime called "86" brought down a list of 2,354 entries**. The 3-item fixtures generated from Xinil contained no numeric title; only validation against the complete real pages caught it. Related, and for the same silent-corruption reason: the `data-items` attribute is read **raw**, not through `capture()` — that helper runs `decodeHtml`, which decodes `&amp;` before `&quot;`, strips anything tag-shaped and collapses repeated whitespace, and each of the three ruins the title or the JSON without raising an error.

**Two completeness guards on the lists (2026-07-30, closing the same batch)**: (1) the page ceiling stopped truncating silently. On leaving the loop with the last page still full, the service now throws **501 `LIST_TOO_LARGE`** instead of storing the prefix — erring high on the page count is preferable to serving half a list, which is exactly the bug this batch fixed. The ceiling rose from 10 to **20 pages (6,000 entries)**; the largest list measured so far has 2,354 (Karinyia, 8 pages). (2) `declaredTotal` stopped being a permanently `null` field in the parser's evidence — **MAL's list page declares no total at all** (the counters next to "All Anime" are drawn by JS), so the field could only lie that completeness had been checked. The real check moved to the service, which compares the assembled list against the `totalEntries` of the profile already persisted in D1: extracting **fewer** than declared now rejects with a 502 and the count in the message (`extracted 273 of 360`), which is the exact signature of AMayacrab's silent truncation. Extracting **more** does not reject — a counter cached before the user added entries legitimately lags behind. With no cached profile there is no counter, and the list is served without the check; the coverage comes from `tests/integration/user-list-guards.test.ts`, which exercises all five paths against a real D1.

**`sourceVersion` left the responses (2026-07-30) — contract change**: the field carried the internal cache-invalidation token (`user-html-v3`, `anime-html-v1`, …) and appeared in the payload of `users/:username`, `users/:username/statistics`, list entries and the details of anime, manga, character, person, club and producer. It was an implementation detail leaking into the contract, and actively misleading: consumers read `user-html-v3` as if the **API** were at v3, when the API version is the `v1` in the path and has never changed. The mechanism is still in place — the `parser_version` column is written in every table and `withCache` compares it on read, so a parser fix still invalidates the snapshot. The catalog repositories already received the version as a separate parameter, so the field inside the entity was duplication; `user.repository.ts` now imports the constant directly. No version bump accompanied the removal (there was no reason to force a mass refetch), so already-written rows still have `sourceVersion` inside `payload_json` — the field disappears for good as each row is rebuilt, within a 6 h TTL cycle.

**Progress cell and entities in the classic layout (2026-07-30)** — found during an API status sweep against AMayacrab's real profile, comparing entry by entry with the MAL page. Two fixes in the same code path, both restricted to the **classic** layout (the modern one reads JSON and was always right):

1. **`progress` came from a different cell.** The context window was `html.slice(start - 1_500, start + 1_500)` — it started **1.5 KB before** the title anchor — and the regex `/<td[^>]*>\s*(\d+)\s*<\/td>/` matched the first digits-only `<td>` it found. Every classic row opens with a position counter (`<td align="center" width="30">1</td>`, which restarts at 1 for each status group), so it was that number, or the neighboring row's, that came out as progress. Measured against the real page: **311 of 360 anime rows** and **all 60 determinable manga rows** wrong (Accel World reported 1 episode instead of 16; *A Returner's Magic* 1 chapter instead of 268). The window is now the row's own `<table>`, never crossing into the previous or next one. The same class as the wide-window bug already fixed twice in the profile parser, now in the list parser.
2. **`total` was discarded and the title carried a raw entity.** The cell has two shapes — `<span id="output918">101</span>/201` for anything in progress (either side can be `-`: unknown total for an airing series, nothing watched in plan-to-watch) and a bare number (`12`) for anything complete, where watched equals total (checked in the source: Acchi Kocchi renders `12` and the anime has 12 episodes; *A Returner's Magic* renders `268` against 268 chapters). The old regex matched neither, hence `total` always `null`. The span id does **not** work as a key — anime uses the MAL id (`output918`), manga uses the list entry id (`chap169785032`) — so what anchors it is the cell, and `width="70"` is what distinguishes it from the position (30), score (45), type (50), tags (125) and priority (80) columns. In the title, the classic path decoded only `&amp;`, so `&quot;` and `&#039;` arrived raw in the API (16 of AMayacrab's 227 manga titles); it now uses the same `decodeEntities` as the modern layout.

`LIST_PARSER_VERSION` rose to `user-list-html-v3` — here the bump is mandatory, unlike the third round of the profile bug: the emitted values change, and without invalidating the cache the wrong entries would survive until the 2 h TTL. The fixtures `tests/fixtures/users/anime-list.html` and `manga-list.html` stopped being hand-written stubs (which **had no progress cell at all**, and that is why the suite passed with the parser broken) and became real rows from AMayacrab's pages, one per status group, with MAL's markup byte for byte. Also validated against the complete real pages: the 360 anime entries and the 227 manga entries match field by field (progress, total, score, title) against an independent extraction from the HTML.

**Random group (implemented 2026-07-26) — a deliberately different policy from Jikan's**: MAL has no public "random" page, and upstream Jikan draws from their complete database. Here, `/v1/random/{anime,manga,characters,people,users}` draws **only from entities already persisted in the local D1** by earlier requests (`ORDER BY RANDOM()`). An empty catalog for that type returns 404 `NO_LOCAL_ENTRIES` — it is not an upstream error, it is just an invitation to fetch a few details first. The bias (it only draws what has already been seen) is intentional and documented; the alternative would be a mass sweep of MAL ids, which the project's rules forbid.

**Fix of 2026-08-27 in the Random group — the group did not agree with itself.** `/v1/random/{anime,manga,characters,people}` returned `meta: { requestId }` while `/v1/random/users` returned the four standard keys (`cached`/`stale`/`refreshFailed`/`fetchedAt`), so anyone reading `meta.fetchedAt` got `undefined` on four of the same group's five routes. All five now emit the four standard keys.

**The `requestId` was removed from those four's success body** (contract change). The test that existed asserted it was there "like every other route" — **it was the reverse**: of the 93 success responses the API builds, that one was the **only** one carrying it. `requestId` belongs in the error body, where it is the correlation handle for support; in a 200 it only made those four the odd shape out. In those four, `stale` is computed here from the row's own `fetched_at` against the catalog TTL, because they are the only reads that do not go through `withCache` and are therefore never refreshed — returning a fixed `stale: false` would be asserting a freshness nobody checked. `cached` is always `true` and `refreshFailed` always `false`: the data comes from the local catalog and nothing was fetched to get it. An unreadable timestamp counts as stale.

**And `/v1/random/users` became `no-store` too** — a real bug, not just a shape inconsistency. It reads a real profile via `withCache`, so it inherited the profile's `Cache-Control` and was served with `public, max-age=21599`: a shared cache would pin **one** "random" user for six hours. It was the only one of the five a CDN could freeze. `X-Cache-Status` stays `local` on the four (nothing upstream is consulted) and hit/miss/stale on the users one, which can genuinely fetch.

**Final parity batch (2026-07-26)**: `GET /v1/producers?q=` (the real directory of ~895 producers at `/anime/producer`, the same format as the magazine directory, with `q` applied locally over the cache), `GET /v1/seasons` (the season archive at `/anime/season/archive`, grouped by descending year), `GET /v1/anime/:id/videos` (the `/x/video` page with three distinct sections: Trailers/PVs, Music Videos and episode videos), `GET /v1/anime/:id/videos/episodes` (a projection of the same page), `GET /v1/anime/:id/episodes/:episode` (the real individual episode page: title, alternative title, duration, air date and synopsis), `GET /v1/anime/:id/themes` (a projection of the `themeSongs` field already extracted by `full` — no new fetch), and `GET /v1/clubs/:id/relations` (the Anime/Manga/Character Relations sections of the club's own page — the same fetch as the detail, separate cache).

Still out (all with documented evidence): per-episode forum, club search (see the note above), `/v1/top/reviews` (see the note above), `/v1/users/:username/history` (see the note above), `/v1/users/:username/external` (the MAL profile exposes no structured external links — there is no real source). `genres/anime|manga` left this list on 2026-07-30 (source changed, see the note above).

## Health and configuration errors

`/health` started including `data.checks.database` on 2026-07-30 (an **additional** field, nothing removed):
`ok` | `not_migrated` | `not_configured` | `unavailable`. The probe is a `SELECT 1 FROM cache_entries LIMIT 1`.
The HTTP status stays **200 even when degraded** — an uptime monitor watches this route, and a broken database
is not the Worker being down; the diagnosis goes in the body.

Alongside came two error codes that only appear on a misconfigured instance, both **503**:

| Code | When | What to do |
| --- | --- | --- |
| `DATABASE_NOT_CONFIGURED` | no D1 bound to the Worker (checked before the route, not inferred from an error) | fix `d1_databases[0].database_id` in `wrangler.jsonc` |
| `DATABASE_NOT_MIGRATED` | D1 bound, no schema (`no such table`) | `npm run db:migrate:remote` |

The reason (issue #1): all 96 routes read `cache_entries` before anything else, so an instance without

stays a 500 — telling someone to run a migration they already ran is worse than saying nothing. See
[`self-hosting.md`](self-hosting.md).

## HTTP cache headers (2026-08-27)

Before this, **none of the 124 calls measured in the sweep returned `Cache-Control`, `ETag` or `Vary`** — only `Content-Type`, `X-Request-Id` and the diagnostic `X-Cache-Status`. In other words: every route was non-cacheable by omission, nothing (browser, CDN, the consumer's HTTP client) could reuse a response or ask whether it had changed, and anyone polling re-downloaded the whole body every time. The heaviest route is 1.13 MB.

- **`Cache-Control` announces the freshness that REMAINS, not the whole TTL.** A resource fetched 5 h ago on a 6 h TTL announces 1 h. Announcing 6 h would leave a shared cache serving for 5 h after this API already considered the data old. A `stale` response announces `max-age=0` to force revalidation instead of propagating the age onward. `stale-while-revalidate` lets the shared cache keep answering during a refresh — it is the same behavior the API has internally **since 2026-08-27** (see below; until then that sentence held only for concurrent requests, not for the one that crossed the TTL), and it spares the consumer the seconds-long wait of a cold miss.
- **The `ETag` is a hash of the body actually sent**, not of `(key, fetchedAt)`. The concrete reason: `meta.cached` flips from `false` to `true` between the request that did the refresh and every read after it, so a tag derived from cache bookkeeping would declare two visibly different bodies identical. Two cached reads of an unchanged resource **are** byte for byte equal (a success response carries no `requestId`), so the 304 fires exactly when it should. 64 bits of SHA-256, costing a few ms on the catalog's largest body.
- **`If-None-Match` is handled as the specification requires**, not with string comparison: the header is a *list*, it accepts `*`, and it can mark entries as weak with `W/`. A simple exact comparison would return the whole body to anyone sending any of those forms, and the failure would look like "revalidation does not work here" rather than a bug — the hardest kind to notice. Weak comparison is the correct one for `If-None-Match` (RFC 9110).
- **Two cases are never cached, on purpose.** Errors are `no-store` (a MAL outage or a 429 held by a CDN would outlive the condition that caused it; on top of that a handler may already have set a success `Cache-Control` before throwing). And `/v1/random/*` is `no-store`: a shared cache holding that would pin one entity and serve it to everybody, the opposite of what the route promises. Four of the five random routes are also the only reads that do **not** go through `withCache`, so they have no TTL to announce — which is why `ttlSeconds` is optional in `ServiceResponse`. **`/v1/random/users` is the exception and that is how it escaped until 2026-08-27**: it goes through `withCache` and inherited the drawn profile's `Cache-Control` (`max-age=21599`), which let a CDN pin one user for six hours; today it overrides with `no-store` like the other four.

### Internal stale-while-revalidate (2026-08-27)

`withCache` already served stale immediately — but **only to whoever arrived alongside**. The request that crossed the TTL acquired the lock and stayed blocked on the fetch to MAL (seconds), while every concurrent request fell into the contended-lock branch and got the old row instantly. The penalty landed on whoever arrived **first**, which is the reverse of reasonable.

Now that request also gets the old row immediately, and the refresh runs behind the response via `ExecutionContext.waitUntil`. Measured live with `wrangler dev --remote` and a 60 s TTL, same route and same page:

| | before this change | now |
| --- | --- | --- |
| cold miss | 1747 ms | 1747 ms (unchanged — there is nothing to serve) |
| fresh hit | 512 ms | 512 ms |
| **first request after the TTL** | did the same work as a cold miss | **686 ms**, `X-Cache-Status: stale` |
| next request | — | `hit`, `max-age=57` — the row was rewritten by the background refresh |

**Four decisions worth more than the code:**

- **The window is one TTL past expiry — exactly what the header's `stale-while-revalidate` already promises.** Internal and announced behavior are now the same rule. A row older than that makes the caller wait: returning weeks-old data would be worse than the wait. An unreadable timestamp also makes it wait.
- **A `parserVersion` mismatch does NOT enter the SWR path.** The failure *fallbacks* still ignore the version on purpose (the alternative there is answering nothing), but here the alternative is waiting a few seconds, and a bump means the stored value is not merely older — it is wrong. The empty genre lists of 2026-08-27 are the concrete case: with indiscriminate SWR, each key would serve the empty list one more time after the deploy. Those callers wait and get the corrected value.
- **The lock is released by the background task, not on the way out.** Releasing earlier would let a second request start a duplicate scrape of the same resource.
- **A background refresh failure has nobody to be reported to** — the caller already got a 200 with the stale body. It goes to `console.warn` as `background_refresh_failed`, and the stored row keeps its old expiry, so the next request tries again instead of backing off.

`waitUntil` is optional throughout the path (`CacheDeps.waitUntil`). Without an `ExecutionContext` — which is the case for the tests' `app.request()` — the refresh runs inline, exactly as before this change; a dangling promise without `waitUntil` can be killed along with the isolate as soon as the response leaves. That is also what keeps the suite deterministic.

The logic is in `src/http/caching.ts` (`cacheControlFor`, `etagFor`, `matchesEtag`), outside `app.ts` precisely so it can be tested without the network — the routes' success path depends on MAL, so the age arithmetic and the tag comparison would have no test if they lived inside the handler.

## Rate limiting

Hardened on 2026-07-27, before public announcement. Two limits per **global IP** (the old key was `IP:route`, which multiplied one IP's budget by the number of routes — ~5,700 req/min across 96 routes; fixed):

- **Burst**: 30 requests / 10 s per IP (`API_BURST_LIMIT`).
- **Sustained**: 60 requests / 60 s per IP (`API_RATE_LIMIT`).

It mirrors Jikan's own public policy (3 req/s, 60 req/min). Exceeded → 429 `RATE_LIMITED` with `Retry-After: 10` (burst) or `60` (sustained). Cloudflare's Rate Limiting API is colo-local and eventually consistent — the cut is not exact at the boundary (verified in production: a burst of 40 requests alternating across different routes produced 429s, confirming the key is global per IP and not per route), so treat the numbers as an operational target, not a rigid contract.

## Cache flow

A fresh hit makes no fetch to MAL. A miss makes one fetch from the source, writes the normalized data and then `cache_entries`. Stale cache is returned if the refresh fails; with no cache, the failure becomes an HTTP error. The lease is per resource and lasts 30 seconds. Since 2026-08-27 the refresh is **no longer synchronous** on the request that crosses the TTL — see "Internal stale-while-revalidate" above.

### D1 row size ceiling and `507 PAYLOAD_TOO_LARGE` (2026-08-27)

A payload too large for D1 to accept was **not** a handled error: `catalog.put` runs inside `refresh()`, so the raw error became "refresh failed" — a 200 with frozen data if an old row existed, a **mute 500** if not (a fresh deploy, or a title requested for the first time). Nothing said the cause was size.

**The ceiling was measured, not read from the docs, and the two numbers diverge.** The [official D1 docs](https://developers.cloudflare.com/d1/platform/limits/) say `Maximum string, BLOB or table row size: 2,000,000 bytes (2 MB)`. Against the real remote D1, writing through a bound parameter exactly as the repositories do:

| bytes | result |
| --- | --- |
| 4,194,256 | writes, and the read comes back byte for byte identical |
| 4,194,257 | `D1_ERROR: string or blob too big: SQLITE_TOOBIG` |

That is 4 MiB (4,194,304) minus the 48 bytes of the other columns — that is, **the ceiling is the row's, not the value's**, confirmed by padding the primary key with 1,000 more bytes and watching the boundary drop by the same amount. **Nothing truncates**: below the ceiling the value always comes back intact. Method: the first probe went through literal SQL (`hex(zeroblob(...))`), which could have been a special path, so it was redone through a bound parameter in a throwaway Worker pointing at the same database.

**Do not build on that headroom.** It is undocumented and could be aligned with the docs at any time; against the **documented** 2 MB ceiling, today's largest row (`catalog:anime:21:characters-staff`, One Piece, 1,207,652 B) is already at 60%. Against the measured ceiling, 28.8%.

**What changed:** `isOversizeRow` recognizes **only** `SQLITE_TOOBIG` — the same discipline as `no such table` → `DATABASE_NOT_MIGRATED`; widening it would report a common bug to the caller as a capacity limit. With no stored copy, it becomes a **507 `PAYLOAD_TOO_LARGE`** (`ServiceErrorStatus` gained the 507; `tests/http/errors.test.ts` verifies that **every** status in the union reaches the client without being coerced to 500). With a stored copy, it keeps serving stale — answering something is still better than not answering — but a `console.error` goes out with `type: payload_too_large`, because this is the failure that **does not resolve itself**: MAL comes back, a document that crossed the ceiling does not shrink. The log goes out the same way when the failure lands in the background refresh.

**507 and not 501.** `LIST_TOO_LARGE` uses 501 and keeps using it: there the limit is ours (a ceiling on pages to fetch). Here the server cannot **store the representation**, which is literally what 507 (RFC 4918) describes.

The lists are obtained from a single public MAL document; the pagination exposed is only D1's, after the snapshot has been persisted. There is no multi-page upstream collection in this slice.
