# Project guide for agents

## State and goal

`jikan-edge` holds the initial vertical slice of **JikanV2** for WeebProfile: Cloudflare Workers, Hono, D1 and parsing of public MyAnimeList HTML. The goal is to validate viability on the Free plan without trying to reproduce Jikan's 100 routes.

The milestone's production code is authorized for user profile, statistics and lists, and — by a decision recorded in `docs/planning/jikan-v4-route-validation.md` ("Expansion decision (2026-07-26)") — for the P0 anime catalog: detail, genres, top and current season. Preserve the separation between source client, pure parser, domain, D1, services and HTTP.

**Full-parity decision (2026-07-26):** the user explicitly decided to widen the scope to every Jikan route (recorded in `docs/planning/jikan-v4-route-validation.md`, section "Full-parity decision"). This supersedes the earlier scope limit — new route groups (manga, characters, people, clubs, producers, seasons, watch, recommendations, reviews, magazines, schedules, search) are now authorized for incremental implementation, following the same per-route quality bar (real page probe, fixture, parser, tests, contract) already used for the anime catalog. Work in progress, in batches.

## Working rules

- Treat Jikan as a functional reference, not as a full-compatibility requirement.
- Use controlled refresh, D1 and stale fallback; never replace valid data with a suspicious document.
- Only use `https://myanimelist.net`; URLs are centralized in `src/source/mal-urls.ts`.
- Do not use a headless browser, internal endpoints, mass scraping or client-supplied URLs.
- Do not widen the scope to every Jikan route without a recorded decision. The full-parity decision (line above) already covers the implemented groups: anime, manga, characters, producers, clubs, people, seasons, watch, recommendations, reviews, magazines, schedules and anime/manga search.
- **When committing any change that affects API consumers** (response contract, a new error code, a visible bug fix, observable cache behavior), **add the corresponding entry to `CHANGELOG.md` in the same commit** — not later, not "when I remember". The entry's content (what, why, before/after) can be written at commit time; only the "Published versions" line depends on a confirmed deploy, because the id only exists after the build. Leave the entry with its date and content ready and an explicit note like "Published version: to be confirmed" rather than inventing an id or skipping the entry — later you just come back and fill in the real id (`npx wrangler deployments list` or the dashboard's Deployments tab).
  - **The Git integration works: every `git push` to `main` triggers a build and deploy, in ~30-60 s** (verified 2026-08-18 in the Builds tab, which lists each build's commit). The earlier note here said the opposite, based on 2026-08-10 — but on that date `pnpm-workspace.yaml` made *every* build fail at dependency installation; `2a6bea6` removed the file on 2026-08-16. "Does not trigger" was a broken build, not asynchronous integration.
  - **Consequence: do not run `wrangler deploy` before `git push`.** It is redundant (the same change ships twice, generating two version ids) and deliberately reintroduces the risk the deploy rule below describes — a manual deploy publishes the *file tree* of that moment, while the build publishes the *commit*. On 2026-08-18 this produced 9 versions for 3 changes. **The id that matters is the one from the build the push triggered**, because it arrives last and is the one left serving.
  - **An entry can never name the version that publishes it.** Any given day's last id can only be filled in afterwards, in a following commit — the absence is structural, not a lost deploy. That was the case for `3853a33d` (2026-08-16), tracked down on 2026-08-18.

- Title-derived anime/manga routes (`relations`, `external`, `streaming`, `characters`, `staff`, `statistics`, `pictures`, `news`, `forum`, and `episodes` for anime only) are implemented — see `docs/routes.md`. `episodes` fetches only MAL's first page (pagination for long series not confirmed).

- `GET /v1/users?q=&page=` implemented 2026-07-26 — see `docs/routes.md`.
- **Club search is blocked by MAL's design, not by missing implementation**: `clubs.php?q=` does not filter server-side (confirmed, same list for any query); the real search depends on an internal endpoint via JS that the rule above already forbids reaching. Do not attempt an implementation without first revisiting `docs/planning/jikan-v4-route-validation.md`.

- **`/v1/top/reviews` investigated and declined, not a missing implementation**: `reviews.php` has no sort by helpfulness/votes, and the date granularity (day only, no time) makes interleaving the anime/manga feeds unreliable. Implementing it would be a redundant alias of `/v1/reviews/anime`/`/v1/reviews/manga`. Do not reopen without new evidence of a real ranking mechanism on MAL.
- `GET /v1/anime/:id/recommendations`, `/v1/manga/:id/recommendations`, `/v1/anime/:id/reviews` and `/v1/manga/:id/reviews` implemented 2026-07-26 — see `docs/routes.md`. **Do not reuse the global parsers** (`recommendations.parser.ts`, `reviews.parser.ts`) for these routes — the per-title structure is different enough (recommendations carry only one side of the pair; reviews do not link back to the title) that reusing them unadjusted breaks silently. They use dedicated `title-recommendations.parser.ts`/`title-reviews.parser.ts`.
- `GET /v1/anime/:id/moreinfo` and `GET /v1/manga/:id/moreinfo` implemented 2026-07-26 — see `docs/routes.md`. Free-form curated text, absent on most titles (returns `{ text: null }`, not an error).
- **`/v1/anime/:id/userupdates` and `/v1/manga/:id/userupdates` are blocked by not existing on MAL, not by missing implementation**: a byte comparison confirmed that this sub-path falls into the detail page's silent fallback (the same behavior as invalid sub-paths). Do not reopen without new evidence of a real page.
- Users group completed 2026-07-26: `full`, `about`, `friends`, `clubs`, `reviews`, `recommendations` implemented (reviews/recs reuse the global parsers with tolerance for empty). `history` not implemented — MAL's page is empty without login; `userupdates` covers the public equivalent. `external` not implemented — no real source in the profile.
- Random group implemented 2026-07-26 with a documented local policy: it draws only from entities already persisted in D1 (`ORDER BY RANDOM()`), 404 `NO_LOCAL_ENTRIES` when the local catalog for that type is empty. It does not sweep MAL ids.

Per-episode forum remains out.
- Functional parity (2026-07-27): server-side search filters on `anime`/`manga` (`type`/`status`/`rating`/`score`/`genres`/`order_by`, all verified against MAL's real behavior; searching by filters alone without `q` is valid), pagination on `reviews/*?page=` (native `p=`) and `recommendations/*?page=` (native `show=`, 100/page), `magazines?q=` (local filter), and `schedules` grouped by day with `?filter=monday..sunday|other|unknown` — **contract change**: without a filter it returns an object keyed by day, no longer a flattened list.
- Fix of 2026-07-27 in the users group (bug reported by a real consumer): profile statistics read the chart's pixel widths instead of the real counters, and `episodesWatched`/`chaptersRead`/`volumesRead` were always `null` (the real labels: `Episodes`/`Chapters`/`Volumes`). Favorites/userupdates now emit `malId` (no longer `mal_id`) and anime/manga favorites carry `startYear`. `PARSER_VERSION` = `user-html-v2`; `withCache` started invalidating cache when `parser_version` diverges. See `docs/routes.md`.
- Follow-up of 2026-07-30 (same bug, fields the 2026-07-27 sweep did not cover): `daysWatched`/`rewatched` (anime) and `daysRead`/`reread` (manga) are now emitted by `/v1/users/:username/statistics`. They had been in the same profile HTML all along — it was not a source limitation. **`Days` is the only stat whose value sits outside a span** (`<span ...>Days: </span>12.5`), so neither `dataValue` nor the `Mean Score` pattern can be reused; `Rewatched`/`Reread` use `dataValue` unchanged. `PARSER_VERSION` = `user-html-v3` (required: `statistics` reads the D1 rows written by the profile refresh, cached under that version). Validated against the real page, not just the fixture. See `docs/routes.md`.
- Third round on the same bug (2026-07-30, coming from PR #2, which was opened from a base without the v2/v3 commits and therefore rediscovered the already-fixed bug): the two earlier fixes anchored the right regexes but kept the fixed 8 KB window starting at `Anime Stats` — and `Manga Stats` sits ~2 KB away, inside the window. Consequence: any line missing from the anime block silently read **the manga number** (confirmed by test: removing the anime `Completed` line, the old parser returned 4, the manga value). Now `statsSection` cuts the anime block at the `Manga Stats` heading and `statsList` restricts each lookup to the correct `<ul>` (`stats-status`/`stats-data`), which also stops generic labels (`Completed`, `Episodes`) from reaching the `Last * Updates` feed just below. **No `PARSER_VERSION` bump** (still `user-html-v3`): no emitted value changes for well-formed pages, so invalidating the cache would be pure refetch cost. `withCache` gained the tests it never had (`tests/services/cacheable.test.ts`).
- **User lists: MAL's modern layout supported and silent truncation fixed (2026-07-30).** `GET /v1/users/:u/animelist` and `/mangalist` returned **502** for every user whose profile uses the modern list layout: the parser only recognized `class="animetitle"` (classic layout), matched zero items, and the completeness guard correctly refused to persist an empty list. In the modern layout MAL embeds the entries as JSON in the `data-items` attribute. **Two findings in the same batch:** (1) without a query param the page carries only *one* entry in the modern layout — the rest would come from `load.json`, an internal endpoint the source policy forbids; the public URL `?status=7` ("All") resolves this by serving the whole list rendered. (2) `?status=7` also fixes **silent loss in the classic layout** — AMayacrab served 273 of 360 entries without the param. Pagination via `&offset=` in blocks of 300 only in the modern layout (the classic one ignores the offset and returns everything at once), with a ceiling of 10 pages. Fields the classic layout never carried now come populated in the modern one (`status`, `total`, `startedAt`, `finishedAt`, `updatedAt`) — **a deliberate asymmetry**: in the classic layout they stay `null`, because the source does not expose them the same way. *(`total` left that list the same day — the classic page does have the number, see the progress-cell bullet below. Before repeating "the source does not expose it", check the page.)* MAL dates are `MM-DD-YY` without a century, converted with a pivot on the current year. `LIST_PARSER_VERSION` is **separate** from the profile's `PARSER_VERSION`, so lists can be invalidated without forcing a refetch of the whole profile. Validated against the complete real pages: 300+99=399 (Xinil) and 360 (AMayacrab), matching field by field against the profile's `totalEntries`. See `docs/routes.md`.
- **A numeric list title arrives as a JSON number (2026-07-30).** MAL does not quote a title that looks like a number — `86` (*86 Eighty-Six*), `1`, `663114`. Reading only strings emptied the title, and an empty title fails the schema; since one invalid item rejects the whole page, an anime named "86" brought down a list of 2,354. It only showed up in validation against complete real pages — small fixtures have no numeric titles. For the same reason (silent corruption), `data-items` is read **raw** and never through `capture()`: its `decodeHtml` decodes `&amp;` before `&quot;`, strips anything tag-shaped and collapses whitespace.
- **Progress cell and entities in the lists' classic layout (2026-07-30).** Found during a status sweep against AMayacrab's real profile. `progress` was read from a window that started **1.5 KB before** the title anchor, and the first digits-only `<td>` in that window is the **row position counter** (`width="30"`, restarting at 1 per status group) — 311 of 360 anime rows and every one of the 60 determinable manga rows came out wrong. The window is now the row's own `<table>`. Alongside: `total` was always `null` even though the source carries it (two cell shapes — `<span id="output918">101</span>/201` while in progress, a bare number when complete, where watched == total), and the title decoded only `&amp;`, leaving `&quot;`/`&#039;` raw. **The span id is not a key**: anime uses the MAL id (`output918`), manga uses the list entry id (`chap169785032`) — anchor on the cell (`width="70"`), not on the id. `LIST_PARSER_VERSION` = `user-list-html-v3` (bump required: emitted values change). The classic fixtures became real MAL rows, one per status group — the old ones were stubs with no progress cell, and that is why the suite passed with the parser broken. See `docs/routes.md`.
- **List completeness guards (2026-07-30).** The page ceiling rose to 20 (6,000 entries) and now throws **501 `LIST_TOO_LARGE`** when the last page still comes back full, instead of silently storing a prefix. And `declaredTotal` left the parser's evidence — **MAL's list page does not declare a total** (the menu counters are JS), so the field could only pretend a check had happened; the real comparison moved to the service, against the profile's `totalEntries` in D1. Fewer than declared → 502 with the count in the message; more than declared → accepted (a stale counter lagging behind is expected); no cached profile → served without the check. Do not reintroduce `declaredTotal` in the parser: there is no source for it on the page.
- **`sourceVersion` removed from public responses (2026-07-30) — contract change.** The field exposed the internal cache-invalidation token (`user-html-v3`, `anime-html-v1`, …) in the payload of profile, statistics, list-entry and the anime/manga/character/person/club/producer details. Practical consequence: readers confused that token with the **API version**, which is and remains `v1` (the `/v1/` in the URL) — that exact misreading is what motivated PR #2. The mechanism is intact: the `parser_version` column is still written in every table and `withCache` still compares it. In the catalog repositories the version was **already** passed as a separate parameter (`.bind(..., fetchedAt, version)`), so the field inside the entity was pure redundancy; in `user.repository.ts` the `PARSER_VERSION` constant is now imported directly. There was **no** version bump, so already-persisted rows keep `sourceVersion` inside `payload_json` until they are rebuilt — the field disappears completely within one TTL cycle (6 h), not instantly. When adding a new entity, do not put the field back in the domain: the version belongs to the cache layer, not to the payload.
- **`genres/anime` and `genres/manga` unblocked on 2026-07-30 by changing the source, not by working around the network.** What MAL truncates for Cloudflare's network is the *sidebar* of the genre browse page (`/anime/genre/1/Action`), not the whole taxonomy: the "Content Filter" block of the search page (`anime.php?cat=genre`) arrives intact at the edge — 78 entries for anime, 79 for manga, confirmed by running the Worker on the real network (`wrangler dev --remote`, config `jikan-edge-remote` in `.claude/launch.json`; use that config whenever the hypothesis depends on *how MAL responds to Cloudflare* — `--local` goes out through the machine's network and reproduces none of this). The 2026-07-19 probe had already measured that same URL at 78 entries through a published Worker, and the original implementation picked the sidebar anyway — probe evidence silently contradicted cost a week of 500s. **Contract change**: each entry is now `{ malId, name, url, count, type }` (`type` ∈ `genres`/`explicit_genres`/`themes`/`demographics`) and the route accepts `?filter=` with those four values. The completeness guard now requires all four categories **and** ≥ 40 entries. `GENRE_PARSER_VERSION` is separate from `ANIME_PARSER_VERSION`/`MANGA_PARSER_VERSION` so only the two genre rows are invalidated.
- **Migration `0009` clears the residual `sourceVersion` from D1 (2026-07-30).** Removing the field (commit `ef51b14`) left the token inside `payload_json` of already-written rows, so it kept showing up in cached responses until the row was rebuilt. `0009_strip_source_version_from_payloads.sql` applies `json_remove(..., '$.sourceVersion')` across the seven payload tables (guarded by `LIKE`, rewriting only what needs it) and deletes the two `catalog:genres:*` rows, whose payload was the truncated taxonomy in the old format. Nothing reads the field: `parser_version` is a column in all those tables. If it shows up again in some new entity, the mistake is in the domain — the version belongs to the cache layer.
- Rate limit hardened on 2026-07-27 (pre-announcement): key per **global** IP (the old `IP:route` multiplied the budget by the number of routes), two bindings — burst 30/10s + sustained 60/60s, with `Retry-After` on the 429. See `docs/routes.md`, section "Rate limiting".
- Public landing page added 2026-07-27 (decision: same repo, not a separate one): static `site/index.html` served by the Worker itself via `assets` in `wrangler.jsonc` (asset-first: `/` serves the site, `/v1/*` and `/health` stay on the Worker). No build step; the page's live demo fetches relative to its own origin. When adding or removing route groups, update the site's route grid and limitations table alongside `docs/routes.md`.
- **Before deploying, check `npx wrangler deployments list`, not just `git status`.** The Worker has no notion of commits: `wrangler deploy` publishes the file tree that exists at that instant. On 2026-07-30 two sessions were working in this repo at once; one published the genres work while it was still **uncommitted**, and the other, publishing the most recent commit from a clean worktree, **undid it without noticing** — genres went back to the old parser and started serving `stale: true, refreshFailed: true` (a 200 with frozen data, which misleads more than the earlier 500). A clean tree is a necessary condition, not a sufficient one: compare the last deploy's timestamp with the last commit's before shipping. Record the published version id in `CHANGELOG.md`, which is the only place where the real unit of delivery stays traceable.
- **Self-hosting unblocked on 2026-07-30 (issue #1, first external consumer).** A third party's deploy answered `500 INTERNAL_ERROR` on **all** 96 routes: they all read `cache_entries` before anything else, and their remote D1 had never been migrated — the README only documented `db:migrate:local` and had no self-hosting section. What changed: `npm run setup` (`scripts/setup.mjs`; the pure helpers are exported and tested in `tests/scripts/setup.test.mjs`, including the regex patch against the **real** `wrangler.jsonc`, so that a reformat of the file breaks in the test and not in the user's hands), `503 DATABASE_NOT_MIGRATED`/`DATABASE_NOT_CONFIGURED` in place of the mute 500, `/health` with `data.checks.database` (still 200 when degraded — an uptime monitor watches that route), and `docs/self-hosting.md`. **Only `no such table` becomes `DATABASE_NOT_MIGRATED`** — do not widen that match to a generic TypeError, or a code bug starts being reported as an operator configuration error. A missing binding is checked by middleware on `/v1/*`, not inferred from an error message.
- **The R2 binding `SNAPSHOTS_BUCKET` was removed on 2026-07-30.** It was never referenced in `src/` (`docs/results/vertical-slice-audit.md` already recorded this and recommended removing it) and forced anyone cloning the project to create a bucket — with an R2 subscription checkout — for nothing. D1 is the only storage. If snapshots come back on the agenda, the binding comes back with the retention design, not before.
- The Free plan is the documented path for self-hosters, **with a measured caveat**: the CPU ceiling is 10 ms per invocation and this API's real corpus lands at p95 27 ms / max 48 ms on a cache miss, so the heaviest routes return `Error 1102` on Free. It is written in `docs/self-hosting.md`; do not promise "runs on Free" without that qualification.
- For platform limits, pricing and APIs, research current official documentation before asserting anything.

### Content parity batch (2026-07-30)

Origin: a paired sweep of the 98 routes against `api.jikan.moe/v4`. **No route was broken** — all 98 answered 200. What showed up was data coming out impoverished, unusable or mislabeled. Per-route detail in `docs/routes.md`, consumer-facing contract in `CHANGELOG.md`.

- **`src/parsers/html.ts` became the real toolbox.** `extractImage` existed in 5 copies (2 byte-identical), `plainLabelValue` in 4, `anchorTexts`/`rankedValue` in 2, and there were **34 inline sites** extracting `imageUrl` with no helper at all. Before touching anything to do with images or labels, check whether the helper already exists there: `imageFrom`, `taggedImage` (+ its four anchors), `labelValue`, `labelBlock`, `anchorTexts`, `anchorRefs`, `canonicalUrl`, `richText`, `richCapture`, `originalImage`, `imageVariants`, `parseDateRange`, `backgroundSection`, `titleSynonyms`. Covered by `tests/parsers/html.test.ts` — which did not exist; the helpers were in production with no direct test.
- **`section` was NOT unified, on purpose**: the 4 variants (`club-relations`, `user-favorites`, `user-profile`, `videos:sectionSlice`) have genuinely different bounds and fallbacks. And `person-detail` keeps its own `tightLabelValue` because "Family name" does not come in its own `<div>` and the shared capture would run into the next field.
- **The order inside `decodeHtml` is loaded**: tags are stripped **before** entities are decoded. The reverse turned a user-written `&lt;b&gt;` into a real tag, which the stripper then ate. A named entity outside the table passes through intact instead of becoming a guess.
- **Long fields use `richText`, not `decodeHtml`** (synopsis, `about`, `moreinfo`, review text, episode synopsis). `decodeHtml` replaces every tag with a space, so MAL's `<br>` became a space and the synopsis came out as a wall of text.
- **`imageUrl` is always the original.** The normalization lives in **exactly one place**, inside `imageFrom`; the 4 anchored sites (`club-members`, `reviews`, `title-reviews`, `user-updates`) apply `originalImage` to the value. **`pictures.parser.ts` stays out on purpose** — there `thumbnailUrl` is a field of its own and the thumbnail is the point.
- **The CDN's image variants are not uniform, and this was measured, not assumed**: anime and manga have `t` and `l`; a character has only `t` (the `l` is a 404); a person has only `l` (the `t` is a 404); a producer logo has no file extension, so it has no variant; a club image 404s on both. `imageVariants` encodes that map and emits `null` where none exists. **Method note**: the first probe said "producer has both" because the logo has no extension, the `replace` did not match and I tested the same URL three times. When probing a variant, confirm the derived URL is **different** from the original before believing the 200.
- **`MalRef {malId, name, url}`** replaced `string[]` in genres/themes/demographics/studios/authors/producers/licensors/serializations. The id was always in the href that `anchorTexts` took only the text from. The real reason: `?genres=1` accepts an id and no response returned one — the loop did not close inside the API itself.
- **The canonical `url` comes from `og:url`**, not from `<link rel="canonical">`: both exist on anime, manga, character, person and producer, but **club and profile only have `og:url`**. Use `canonicalUrl()`, which tries og:url first.
- **Search is two types, not one.** `AnimeSearchEntry` (`episodes`) and `MangaSearchEntry` (`volumes`), with separate cache versions. Do not re-unify: the middle column of the manga results table is **volumes** — Fullmetal Alchemist returned `episodes: 27`, and 27 is its volume count (chapters are 116). It was the right number with the wrong label, not a dead field.
- **Synthetic fixtures hide a missing field.** The detail ones had no `og:url`, `Premiered`, `ratingCount` or `Background` — a new parser would pass the test while extracting nothing. `tests/fixtures/{anime,manga}/detail-real.html` are byte-for-byte excerpts of the real page. When recapturing, **check field by field what the fixture contains**, not just whether the test passes: my first excerpt stopped at the first `</td>`, which comes before `Studios`/`Producers`/`ratingValue`.
- ~~**`tsconfig.json` excludes `tests/integration/**`**, so the factories that build the complete domain object are **not typechecked**.~~ **Out of date — fixed in `1ab73cf` (2026-07-30), verified 2026-08-27.** `tsconfig.json` no longer has an `exclude`; the `include` is `["src/**/*.ts", "tests/**/*.ts"]` and the integration factories **are** typechecked. Confirmed in practice, not by reading: when `RandomService.pick()`'s signature changed on 2026-08-27, it was `tsc` that pointed at the broken cast in `tests/integration/catalog.test.ts`, not a manual check. **The manual check this bullet used to mandate is no longer necessary.** Method note: `1ab73cf` itself edited this file — but a different section of it — and left this bullet behind, which kept the wrong instruction in force for almost a month. When fixing a problem this file describes, look for **every** mention of it here, not only the one in the section you happen to be working in.
- **No batch shell editing of a file containing a non-ASCII character.** The rule holds for *any* tool that rewrites the whole file, not just PowerShell: `Get-Content`/`Set-Content` without `-Encoding` read UTF-8 as ANSI and `宏一` becomes `å®ä¸€`; `perl -pi` without `use open qw(:std :utf8)` does the same damage in the other direction, and in-place `sed`/`awk` depend on the locale. Use the editing tool, or Node with `readFileSync(f, 'utf8')` + `writeFileSync(f, s, 'utf8')`.
  - Real cost (2026-08-18): a `perl -0pi -e` inserting meta tags into the four HTML files in `site/` turned every `—` into `â` and every `時` into `æ`. The `Wide character in print` that perl prints **is** the corruption warning — it is not noise. Recovered with `git checkout --`, which only worked because the earlier work was already committed; in one larger commit it would have been real loss.
  - Encoding corruption breaks neither tests nor typecheck — the files in `site/` are not compiled, and `grep` for ASCII keeps matching. **After any batch edit, verify explicitly**: `node -e "const s=require('fs').readFileSync(f,'utf8'); console.log(s.includes('時'), /â€|Ã§|æ—/.test(s))"`. Check what the server delivers too, not only the file on disk. (Running that check **on this file** always reports positive: the patterns match the example above. Confirm *where* it matched before believing a finding — in any file, for that matter.)

- **Line endings are in the same family as encoding, and just as invisible: check the diffstat before committing.** `.gitattributes` has `* -text` precisely so Git converts nothing in either direction — but that protects against *Git's conversion*, not against the editing tool writing the file with the wrong line ending. When that happens, Git sees **every** line rewritten.
  - Real cost (2026-08-27): commit `f7426e7` reported 697 insertions and 530 deletions for a 65-line change — `anime.service.ts`, `mal-client.ts` and `mal-client.test.ts` went in with CRLF in a repo whose `src/`/`tests/` is all LF. Fixed in `c7045c5`, but the dirty commit was already published; reviewing what actually changed became archaeology.
  - **Neither tests nor typecheck report it** — the 295 tests passed and `tsc` was clean with the line endings swapped. The only signal was the diffstat. So: **after editing, look at `git diff --stat` and compare it against the size of the change you made**; if it does not match, confirm with `git diff --stat --ignore-cr-at-eol` (the difference between the two numbers *is* the line-ending churn).
  - To fix it without touching the content, use Node (`s.replace(/\r\n/g, '\n')` with `readFileSync`/`writeFileSync` in `'utf8'`), never `dos2unix`/`sed` — that falls under the encoding rule above.
  - **Normalize only what you flipped yourself.** `docs/routes.md`, `site/*` and **this file** are CRLF by origin; converting those would be the same unrequested churn in the opposite direction. Before "fixing" anything, check what the file was: `git show <previous-commit>:<file> | node -e "...count \r\n..."`.

### Query param validation and pagination (2026-07-30)

- **`src/http/query-contract.ts` is the source of truth for what each route accepts**, and `tests/routes/query-contract.test.ts` enumerates `app.routes` and fails if any GET route has no entry. A new route with no entry = a red test, not a silently absent guard.
- **A catch-all on `/v1/*` would not work**: Hono composes middleware in registration order rather than letting the specific one override the generic, so the generic would reject `?q=` before the route that accepts it ran. That is why it is one middleware per route pattern, registered in a loop.
- **Do not put a parameter in the table before implementing it.** Doing so recreates exactly the defect the guard eliminates — an accepted parameter that does nothing.
- **A badly built probe produces a "does not work" that turns into a wrong decision.** `start_date`/`end_date` were declared unviable and published as `UNSUPPORTED_PARAMETER` on the basis of a probe that ran with an empty `q=` — which returns the default alphabetical dump — and that did not check the semantics of the result. The fields exist (`sm`/`sd`/`sy` and `em`/`ed`/`ey`, month-day-year order) and they filter. Before recording "the source does not support it", **read the real form** instead of guessing names, use a query with actual results, and **check the meaning** of what came back (here: the premiere dates in the detail), not just the count.
- **`?filter=` on `top/*` has a different vocabulary per medium, and MAL does not warn when it ignores one.** Anime accepts Jikan's four; manga accepts only `bypopularity` and `favorite`, because `topmanga.php` has no publishing/upcoming tab and returns the list unfiltered (measured by comparing id sets: 50 of 50 identical). An unknown `type=` answers 200 with the unfiltered list — which is why the validation is ours, in `services/top-filter.ts`. When adding a new filter to any route, **compare the result's ids against the call without the filter** before believing it worked; a 200 does not prove filtering.
- Two codes, and the distinction is the point: `UNKNOWN_PARAMETER` (a name that does not exist) and `UNSUPPORTED_PARAMETER` (exists in Jikan, not honored here — the message says why). Someone porting from Jikan needs to know whether they got the name wrong or the feature does not exist.
- **`MAX_PAGE = 1000`** because each distinct page number fires a real request to MAL and writes a cache row — measured at 1.5 s to 8.6 s for `?page=200`.
- **Page sizes are constants in `mal-urls.ts`.** The routes with `show=(page-1)*N` already carried them in the arithmetic; the two with `?p=` carried no number at all and were **measured**: `clubs.php` serves 50, a **per-title** review page serves 20. `docs/routes.md` said 50 for reviews, but that is the global list — using 50 would make `hasNextPage` wrong on every title review page.
- **`total` is `null` outside the user lists**, and should stay that way: MAL does not print a total, and deriving one from `lastVisiblePage × perPage` would be an invented number in the `meta` of an API that removed a field for being misleading.
- **`genres_exclude` does not coexist with `genres`**: MAL's `gx=1` **inverts** the sense of every `genre[]` in the request rather than adding an exclusion (`genre[]=12` → 17 results; `genre[]=12&gx=1` → 20 disjoint ones). Passing both is a contradiction and is refused.

### Cache decisions that should not be revisited

- **The stale fallback does NOT check `parserVersion`, and that is a choice.** It was implemented and reverted in that session. The test at `cacheable.test.ts:42` already documented the reason: refusing there gives up exactly the property that defines this API — answering while MyAnimeList is down. Measured the same day: 81 of Jikan's 94 routes returning 504 (`"Jikan failed to connect to MyAnimeList"`) while ours served, with MAL responding normally to us. Most bumps change a **value**, not a shape, and in those the old payload is valid, just worse. The dangerous case (a shape change) is handled in a targeted way by the migration that deletes those rows — see `0010`.
- **`TOP_ANIME_/TOP_MANGA_/SEASON_PARSER_VERSION` are separate from `ANIME_/MANGA_PARSER_VERSION`.** They used to be the same, and touching the format of a *list* forced a refetch of **every cached anime detail**. When creating a new list route, give it its own version.
- **The cache key always carries `:page:N`, including page 1.** `reviews`/`recommendations` made an exception for the first page; migration `0011` renamed the four rows that would have been orphaned, moving `catalog_lists` and `cache_entries` together.

### Full review and robustness fix batch (2026-08-10)

Origin: a review of the whole codebase (not a route sweep against Jikan, like the earlier ones) explicitly requested by the user, split into "Tier 1" findings (confirmed bug, fix now) and "Tier 2" (worth doing, not urgent). Every finding was verified against the real MAL page or by test before becoming a fix — none was fixed by code inspection alone.

**Tier 1 (real production bugs):**

- **`anime-full.parser.ts` — `themeSongs` came out empty/partial.** MAL is gradually replacing the openings/endings widget; the parser only recognized `<span class="theme-song-title">"Title"</span>` (the old format). The new format puts the title as loose text between quotes right after `<span class="theme-song-index">N:</span>`, with no title span at all. Confirmed live: Frieren (100% new format) returned `{openings:[], endings:[]}`; Fullmetal Alchemist: Brotherhood mixes both formats on the same page. The parser now tries both formats per line. `ANIME_FULL_PARSER_VERSION` v2→v3.
- **`characters-staff.parser.ts` — `parseStaff` cut the Staff section at a fixed 80 KB ceiling.** Confirmed live against One Piece: the real staff is 543 KB with no intermediate heading at all, so the cut extracted 80 of 542 members — ~85% lost silently. Fixed to the same pattern as `backgroundSection`: cut at the next real heading, or at the end of the document if there is none. `CHARACTERS_STAFF_PARSER_VERSION` v2→v3.
- **`app.ts` — the query param guard for `/health` was dead code.** `registerQueryGuards(app)` was called *after* `app.get('/health', ...)` had already been registered — Hono composes middleware in registration order, so the guard never reached that route. `GET /health?bogus=1` answered 200 instead of the 400 that `QUERY_CONTRACT['/health'] = []` itself promises. Confirmed by a real test hitting the route, not just by reading code. Fixed by moving the guard registration before the `/health` handler.
- **`cacheable.ts` — a failure writing `cache_entries` discarded new data that was already persisted.** `deps.cache.put(...)` (the bookkeeping write to `cache_entries`) was inside the same `try` as `refresh()`. If `refresh()` had already written the new value into the domain table and only the `cache_entries` write failed (a transient D1 blip), the catch returned the **old** data labeled `refreshFailed: true`, even though the new one was already saved. The bookkeeping write now has its own best-effort try/catch, separate from `refresh()`.
- **`search.service.ts` — a user search with no recognized page became a generic 500 instead of a 502.** `getHtml(userSearchUrl(...), [])` had no `requiredMarkers`, and `parseUserSearch`'s fallback to a single profile page is deliberately tolerant (it exists to degrade well on a real, incomplete profile page) — without a guard, that let arbitrary HTML (not a results list, not a real profile) pass as a valid profile match, with username = the query itself, instead of failing. Fixed in the parser (`user-search.parser.ts`): it requires the `Anime Stats` marker before attempting the profile fallback; the resulting `ParserError` now becomes `502 UPSTREAM_SUSPICIOUS` instead of leaking as a `500`.
- **`updates.repository.ts` — hardcoded parser version, never updated.** The only one of the 10 repositories that did not follow the common `(key, value, fetchedAt, version)` signature: `put()` ignored the version parameter and wrote the literal `'user-html-v1:updates'` every time, and the `ON CONFLICT` did not even include `parser_version` in the updated column list — it froze at the first insert. It did not break the live response (the real invalidation goes through `cache_entries`, which was always correct), but it left the table's own bookkeeping lying. Fixed; migration `0012` backfills the real value from `cache_entries` for the already-written rows.

**Tier 2 (implemented in that session, at the user's explicit request):**

- `withCache` gained an optional `leaseSeconds` (default: `RefreshLockRepository`'s 30s). `user.service.ts`'s `mediaList` (which can make up to `MAX_LIST_PAGES` sequential fetches) now passes a lease sized for the real worst case (`listRefreshLeaseSeconds`), so it does not lose the lock in the middle of a long refresh and let a second request start a redundant scrape in parallel.
- `ServiceError.status` became a literal union (`400|403|404|429|501|502|503|504`, exported as `ServiceErrorStatus`) instead of `number` with `as 400` in `errors.ts` — the cast was lying to the type system that every error is a 400.
- **`ClubDetail.staff` changed from `string[]` (`"Name (Role)"`) to `{ username, url, role }[]`** — the same class of fix as `MalRef` from 2026-07-30: the regex already captured the profile href and threw it away; the concatenated string was also ambiguous if the name or role contained parentheses. `CLUB_PARSER_VERSION` v2→v3. See the note in `docs/routes.md`.
- `MalClient.getHtml` gained 1 retry (200ms backoff) only for `upstream_error`/`timeout` — not for `suspicious`/`not_found`/`private`/`rate_limited`, which are deterministic responses where repeating changes nothing. A cold cache miss (with no stale to fall back to) did not have that safety net before.
- `character-detail.parser.ts` — the same pattern as the `parseStaff` fix, applied preventively: `extractAbout` no longer cuts at a fixed 4,000 chars when "About" is the last section on the page. **No `CHARACTER_PARSER_VERSION` bump**: unlike the Tier 1 fixes, this one had no confirmed live reproduction — forcing a refetch of the entire character catalog over a hypothetical case was not worth the cost.
- **New pattern: cache priming between `detail()`/`full()`/`media()` of the same entity.** `anime`, `producer` (`detail`↔`full`, 2-way) and `character`/`person` (`detail`↔`full`↔`media`, **3-way** — worse than the original mapping predicted) read the same detail page URL entirely independently: a client hitting `/full` right after `/detail` fired a second real fetch to MAL for the same page. Now, whenever one of those routes does a real refresh (cache miss/stale), it also writes the sibling routes' cache (the domain table **and** `cache_entries`, replicating what `withCache` would have written) from the HTML it already has in hand — reads stay independent and cheap, only the write at refresh time is shared. Best-effort: a priming failure does not bring down the main request (`console.warn`, carry on). **Always strip the extra fields of the wider shape before writing to the narrower cache** (`themeSongs` out of `detail`, `about`/`external` out of the producer's `detail`, `anime`/`manga`/`voices` out of character/person `detail`) — otherwise the field leaks into a route that never promised it. **No version bump on any of these** — priming changes how many times MAL is fetched, not the value or shape of any response. If you add a fourth route derived from the same detail page in the future, extend this pattern rather than reinventing it (see `writeSiblingCaches` in `character.service.ts`/`person.service.ts` for the 3+-way case).

## Commit hook

`.githooks/commit-msg` strips AI attribution trailers from commit messages. Git does not version
`.git/hooks`, so what makes the hook run is one line of local config — and a fresh clone does not
have it. The root `prepare` script sets it on `pnpm install`, and only when nothing else claims it:

```
git config --get core.hooksPath >/dev/null 2>&1 || git config core.hooksPath .githooks
```

If you already point `core.hooksPath` somewhere else, the script leaves your value alone and this
repo's hook stays inert — wire it by hand, or move the file into whatever directory you do use.
